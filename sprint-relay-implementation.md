# SprintRelay — Codex implementation brief

## Goal and scope
Build a reusable, small-team hackathon management system. Priority: reduce administrative effort, prevent cross-team misunderstandings and conflicts, visualize progress, then experiment with AI. GitHub is the canonical source for specs, issues and project status. Discord is the interaction layer, particularly for non-engineers. Do not build a separate full project-management platform.

## Requirements
- Team: fixed roles: design (2), frontend (1), backend (1), hardware (1). Use configuration for Discord IDs, GitHub usernames, repository/project IDs, channels and authorized approvers. Assign engineering tasks deterministically by role; design tasks go to the team and may be claimed in Discord. No automatic reassignment. Cross-team tasks have a primary owner.
- External transcription: accept text or .md/.txt attachment submitted to a designated Discord channel. Do not implement recording/transcription. Explicit import command or confirmation; preserve source reference, separate proposals, decisions and open questions. Store sensitive records only in an authorized private location. Require participant consent for external AI processing.
- Specification workflow: AI extracts meeting minutes and decisions, drafts Markdown spec with stable requirement IDs, purpose, scope, functional/nonfunctional requirements, interfaces, ownership, acceptance criteria and open questions. Humans review and edit. At least one AI consistency check on the revised version is mandatory; check technical/logical/cross-team consistency, completeness, feasibility and decision traceability. AI may normalize language, remove duplication and clarify without changing meaning; material changes (features, technology, interfaces, scope) require human decision. Keep versioned diffs and reasons, never silently reverse human edits. If blocking questions remain, return for revision. Authorized final human approval binds to a specific validated revision; then generate tasks automatically.
- Tasks: structured output, 1–4 estimated work hours per task, independent deliverable and testable acceptance criteria; split large tasks, merge trivial tasks where appropriate. Include stable key, repo/issue reference, title, description, role, assignee, status, priority, estimated/remaining effort, dependency keys, requirement IDs, deliverables, optional deadline, baseline and forecast dates, observed start/end and CPM metrics. Validate missing/duplicate keys, invalid roles, unknown dependencies and cycles before creating issues. Idempotent creation and recovery from partial failures. GitHub Issues and Projects integration, link PRs; design outputs may use external URLs. Status Todo, In Progress, In Review, Blocked, Done, Cancelled. Review rejection returns to In Progress. Only valid completion/acceptance can close a task. Discord and GitHub operations share canonical state.
- Scheduling: configurable start/end, feature freeze, timezone (default Asia/Tokyo), buffer, milestones and per-member availability intervals. No hard-coded hackathon dates or 24h availability assumption. Compute deterministic DAG/CPM (ES/EF/LS/LF/total float, critical paths, dependency-only minimum duration). Distinguish dependency-only CPM from resource-constrained calendar forecast. Implement a simple deterministic list scheduler honoring dependencies, fixed role/owner, individual availability and no overlapping work per person; design pool max 2, respect claimed owner; no optimality claim. Flag infeasibility and unknown remaining time/blocked resolution rather than silently invent estimates. Preserve original baseline and actual timestamps; recalculate remaining schedule on completion, estimates, blocking/unblocking, dependencies, scope, availability or project-period changes, and periodic overdue check. Never automatically move contractual deadlines, reassign people or reduce scope. Show risks and suggested options; humans decide. Timezone-aware timestamps internally, hour/minute resolution for short events. Handle cancelled dependencies explicitly. Include buffer without double counting.
- Visualization: GitHub Projects board/roadmap where supported; generate hour-resolution Gantt chart with baseline, forecast, actuals, critical path and deadline/milestones; display on Discord. Progress reports include status counts, by-role workload, remaining effort, blockers, critical tasks, forecast and risks. Progress counts/effort are not individual performance measures. Notify when dependencies clear, critical risks/blocks arise, review is requested or CI fails; dedupe and aggregate low-value notifications.
- Discord UI: minimal channels configurable; import meeting, draft/revise/validate/approve spec, create/list/mine/claim/start/review/done/block/unblock/estimate tasks, show/update/recalculate schedule and critical path, progress. Buttons/forms for common task actions. Authenticate/authorize by Discord ID and role, use appropriate visibility. GitHub event synchronization via supported webhooks/Actions or polling, reconcile concurrent updates and prevent event loops. Verify webhooks if used. Discord-only design users must not need GitHub login to manage tasks.
- Scope changes: provisional policy: auto-update unstarted tasks after approved changes; active tasks require owner approval, review-stage tasks notify, completed tasks use new follow-up issues, obsolete tasks are cancellation candidates (not deleted). Recompute dependencies and forecasts. Major changes follow full spec approval process.
- AI: Meta Muse preferred for natural-language tasks; Codex for technical review, coding and tests. Verify actual API/access and model availability; do not assume a consumer agent has a public API. Provider adapters with typed structured results and mock provider; manual fallback or configurable supported alternative. No LLM for deterministic scheduling, counts, fixed assignment, API actions or authorization. Treat transcripts, issue content and model output as untrusted data; no execution of model-generated commands. No credentials or actual meeting content committed. Minimal token scopes and explicit approval gates. No automatic merging.

## Suggested implementation
Python, discord.py, Pydantic, GitHub REST/GraphQL, NetworkX or pure Python, Plotly or another simple chart output, YAML, Markdown, SQLite for workflow state/idempotency/cache only (GitHub remains canonical for tasks/specs), pytest. Single deployable service for Linux/LXC; avoid microservices. Provide .env.example, .gitignore, configuration examples, README, AGENTS.md, docs, CI and tests. Separate the management repo from the product repo and allow configuration of product repo(s). No real Discord/GitHub/AI credentials are required to run unit and mocked integration tests.

## Implementation sequence
1. Bootstrap repository, data models, config, state and GitHub/Discord adapter skeleton. Implement task CRUD/status/claim and notification flow with mocked tests.
2. Meeting import, decision extraction, versioned spec drafting and human review/approval gate, mandatory consistency pass, validated task generation and idempotent GitHub issue/project publishing.
3. Dependency graph, CPM, fixed-owner calendar scheduler, rescheduling, Gantt and risk notifications. Tests for cycles, parallel tasks, same-owner conflicts, timezones, breaks, deadline changes, blocked tasks and unknown inputs.
4. Codex integration if officially supported, AI progress summaries and change-impact workflow. Document unsupported integrations honestly and preserve manual alternatives.

## Acceptance criteria
End-to-end mocked demonstration: transcript → draft → human revision → consistency check → approval → tasks → issues/projects → Discord/GitHub task operations → schedule → delay/period change recalculation → notification. Verify approval cannot be bypassed or reused for a changed revision, duplicate input cannot create duplicate issues, invalid DAG does not publish tasks, unavailable AI does not prevent manual work, no overlapping assigned work, actual dates/baseline are preserved, and hard deadlines never move automatically. Test with fixtures, not live secrets; document live setup and what has not been verified. Use incremental commits and submit a reviewable PR rather than merging directly. Keep setup/operation simple; prioritize usable functionality over unnecessary abstractions.
